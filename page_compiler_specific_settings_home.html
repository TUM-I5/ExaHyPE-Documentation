Peano keeps system- and compiler-specific settings in two places:

  • The build configuration is driven entirely by CMake. Optional features such as GPU backends and I/O libraries are selected through PEANO_WITH_* options, and the resulting preprocessor defines and compiler and linker flags are attached to the PeanoOptions interface target, so every library and application built on top of Peano inherits them. CMake also writes a PeanoConfig.cmake file into the build directory; the Python API reads this file to learn about the configuration and to generate consistent makefiles for the codes built on top of Peano.
  • At compile time, a single header derives a small set of portability macros from the compiler that is actually in use (through standard predefined preprocessor symbols such as __NVCOMPILER, __GNUC__ or __clang__). This header hides the differences between the compilers from the rest of the code.

The page below discusses how to build Peano with the major vendor toolchains and provides some hints on compiler and linker flags for each of them. Before the particular toolchains, a general remark on how the compiler dependencies are managed:

Realisation of Peano's internal compiler-specific switches

Peano relies on a single header tarch/CompilerSpecificSettings.h. This header inspects the predefined macros of the compiler in use and, on this basis, defines a small set of portability macros (alignment hints, inlining attributes, SIMD and unrolling pragmas, and switches for compilers that do not support certain OpenMP constructs).

Whenever we find incompatibilities between different compilers, we try to resolve them through defines within this header. This way, we avoid that some "fixes" are spread over the whole code. Most expressions within the compiler-specific settings header can manually be overwritten via defines. Consult the file itself for details.

The build defines provided by CMake (for example PEANO_WITH_ALIGNMENT or PEANO_WITH_SIMDLEN) feed into this header. Whenever certain macro combinations have knock-on effects on other features, they are evaluated here and mapped onto further portability macros.

There are exceptions to this rule: If you have a certain GPU backend, you might have to annotate functions in a certain way. Such information is not covered within CompilerSpecificSettings (it has nothing to do with a particular compiler choice), but is found directly within the headers of the respective namespace in the technical architecture.

Vendor toolchains and compiler settings

All builds use CMake. The recipes below set the compiler via the standard -DCMAKE_CXX_COMPILER / -DCMAKE_C_COMPILER switches, toggle features through PEANO_WITH_* options, and pass any vendor-specific compiler or linker flags via the semicolon-separated lists PEANO_EXTRA_CXX_FLAGS and PEANO_EXTRA_LINK_FLAGS. The C++ standard is fixed to C++20. The general shape of a configure call is

mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=... [options]
make -j

Most GPU backends derive the actual offloading flags themselves from the chosen backend (PEANO_WITH_GPU_BACKEND) and the target architecture (PEANO_WITH_GPU_ARCH, e.g. sm_90, gfx90a or spir64), so for those you usually do not have to spell out the offloading flags by hand.

GNU

OpenMP and OpenMP offloading

GCC offers OpenMP host threading out of the box and OpenMP GPU offloading via PEANO_WITH_GPU_BACKEND=ompt. The OMPT backend selects the matching -foffload=... flag for the requested architecture automatically.

cmake .. -DCMAKE_BUILD_TYPE=Release \
-DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++ \
-DPEANO_WITH_GPU_BACKEND=ompt -DPEANO_WITH_GPU_ARCH=sm_90 \
-DPEANO_EXTRA_CXX_FLAGS="-march=native"

Drop the two GPU options (and the architecture) for a pure host build.

Intel (oneAPI)

The Intel oneAPI compilers are icx (C) and icpx (C++). Select them through the standard CMake compiler switches.

Build modes and tracing

Trace and annotation data only become available if you do not build in release mode. Switch to the assertions or the debug mode - compare the general remarks on Peano's build variants - to get traces or annotation information. For further discussion on logging, please see the generic logging description for Peano.

If you analyse threaded runs with the Intel tools, the following flags are useful raw compiler hints. They are passed via PEANO_EXTRA_CXX_FLAGS:

  • -DTBB_USE_THREADING_TOOLS -parallel-source-info=2 for all builds, and
  • additionally -DTBB_USE_ASSERT for debug and assert builds.

OpenMP and OpenMP offloading

For Intel GPUs use the OMPT backend with the spir64 target. The backend adds -fopenmp-targets=spir64 for you; -fiopenmp is Intel's recommended OpenMP front-end flag for performance and features.

cmake .. -DCMAKE_BUILD_TYPE=Release \
-DCMAKE_C_COMPILER=icx -DCMAKE_CXX_COMPILER=icpx \
-DPEANO_WITH_GPU_BACKEND=ompt -DPEANO_WITH_GPU_ARCH=spir64 \
-DPEANO_EXTRA_CXX_FLAGS="-fiopenmp;-march=native"

SYCL and SYCL offloading

SYCL is directly supported via icpx. Select it as the C++ compiler and pick a SYCL-capable GPU backend (native with an Intel spir64 architecture, or acpp). The build adds -fsycl -fsycl-targets=spir64 for you, which makes all SYCL headers known to icpx and tells the linker to add the SYCL libraries and to embed both the device and the host kernels into the executable.

cmake .. -DCMAKE_BUILD_TYPE=Release \
-DCMAKE_C_COMPILER=icx -DCMAKE_CXX_COMPILER=icpx \
-DPEANO_WITH_GPU_BACKEND=native -DPEANO_WITH_GPU_ARCH=spir64

If you add -lsycl alone and leave the linking to the plain linker, the build succeeds, but the very first time you invoke a SYCL kernel you get a message similar to

terminate called after throwing an instance of 'sycl::_V1::runtime_error'
what(): No kernel named <mangled SYCL kernel symbol> was found -46 (PI_ERROR_INVALID_KERNEL_NAME)
Aborted (core dumped)

To offload SYCL onto NVIDIA or AMD GPUs through the oneAPI plugins (Intel LLVM, Codeplay), set PEANO_WITH_GPU_ARCH to the corresponding sm_XX (NVIDIA) or gfxXXX (AMD) architecture and add the matching SYCL target as a raw compiler and linker hint, for example via

-DPEANO_EXTRA_CXX_FLAGS="-fsycl-targets=nvptx64-nvidia-cuda;-fp-model=consistent"
-DPEANO_EXTRA_LINK_FLAGS="-fsycl-targets=nvptx64-nvidia-cuda"

(or -fsycl-targets=amdgcn-amd-amdhsa for AMD), where the architecture itself is supplied through PEANO_WITH_GPU_ARCH.

MPI

Intel's MPI compiler wrapper is mpiicpc, and oneAPI expects icpx as its C++ compiler. To make the wrapper call icpx, export the corresponding environment variable and point the CMake compiler at the wrapper:

export I_MPI_CXX=icpx
cmake .. -DCMAKE_CXX_COMPILER=mpiicpc

LLVM

OpenMP

Clang offers OpenMP GPU offloading through the OMPT backend. The backend derives the -fopenmp-targets=nvptx64-nvidia-cuda --offload-arch=... flags from the requested architecture, so you only have to name the backend and the GPU architecture.

cmake .. -DCMAKE_BUILD_TYPE=Release \
-DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
-DPEANO_WITH_GPU_BACKEND=ompt -DPEANO_WITH_GPU_ARCH=sm_90 \
-DPEANO_EXTRA_CXX_FLAGS="-march=native"

Replace sm_90 by the actual compute capability of the device.

NVIDIA NVC++ (NVHPC)

The NVIDIA HPC compiler is nvc++. As nvc++ is also used as the C compiler in this toolchain, point both CMAKE_C_COMPILER and CMAKE_CXX_COMPILER at it.

OpenMP and OpenMP offloading

NVIDIA's compiler supports a subset of recent OpenMP task features. CMake tests whether iterator expressions are accepted in task dependencies; when the probe fails, the tasking layer uses conservative dependency waits that preserve ordering with less parallelism.

The OMPT backend translates the requested architecture into the -mp=gpu -gpu=ccXX flags that NVHPC expects:

cmake .. -DCMAKE_BUILD_TYPE=Release \
-DCMAKE_C_COMPILER=nvc++ -DCMAKE_CXX_COMPILER=nvc++ \
-DPEANO_WITH_GPU_BACKEND=ompt -DPEANO_WITH_GPU_ARCH=sm_90 \
-DPEANO_EXTRA_CXX_FLAGS="--diag_suppress=unrecognized_attribute;-Munroll=c:100;-march=native"

Replace sm_90 by the actual compute capability of the device. To experiment with C++ standard parallelism offloading you can add -stdpar=gpu to PEANO_EXTRA_CXX_FLAGS.

AMD

For the AMD toolchain you need to load either ROCm or AOMP. Both modules ship AMD's modified version of Clang, amdclang/amdclang++. Point both CMake compiler variables at it.

OpenMP and OpenMP offloading

The OMPT backend emits the AMD offloading flags (-fopenmp-targets=amdgcn-amd-amdhsa --offload-arch=gfxXXX) for the requested architecture:

cmake .. -DCMAKE_BUILD_TYPE=Release \
-DCMAKE_C_COMPILER=amdclang -DCMAKE_CXX_COMPILER=amdclang++ \
-DPEANO_WITH_GPU_BACKEND=ompt -DPEANO_WITH_GPU_ARCH=gfx90a \
-DPEANO_EXTRA_CXX_FLAGS="-march=native"

Replace gfx90a by the actual architecture of the device.
