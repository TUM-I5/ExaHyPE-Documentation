Boundary conditions

Boundary conditions are determined entirely by the user's boundaryConditions callback. This means one solver can impose different boundary conditions in different parts of the domain, as long as the callback sets the outside state consistently.

For finite-volume solvers, ExaHyPE calls boundaryConditions for each volume adjacent to the domain boundary before a patch update. The callback receives the inside state and writes the halo state outside the domain. Discontinuous Galerkin schemes use the same idea at their boundary degrees of freedom.

Boundary conditions on Cartesian boxes

Dirichlet boundary conditions

Dirichlet data prescribe the solution on the boundary:

\[ Q(x)\vert_{\partial\Omega} = f(x,t). \]

The simplest implementation writes the desired value directly into the outside state:

void MySolver::boundaryConditions(...) {
Qoutside[0] = value0;
Qoutside[1] = value1;
}

For some schemes it is preferable to account for the numerical flux using the average of the interior and exterior states. If the flux sees

\[ \frac{1}{2}\left(Q_\text{outside} + Q_\text{inside}\right) = f(x,t), \]

then the outside state should be

\[ Q_\text{outside} = 2f(x,t)-Q_\text{inside}. \]

With Rusanov-type solvers you may also need to choose the outside state so the eigenvalue term at the boundary has the intended value.

Neumann boundary conditions

Homogeneous Neumann conditions require a vanishing normal derivative:

\[ \left(\nabla Q(x), n\right)\vert_{\partial\Omega} = 0. \]

For a Cartesian halo this is usually implemented by copying the interior state:

void MySolver::boundaryConditions(...) {
Qoutside[0] = Qinside[0];
Qoutside[1] = Qinside[1];
}

Non-homogeneous Neumann data can be imposed with a finite-difference reconstruction of the outside value.

Inflow and outflow conditions

Inflow and outflow conditions are conceptually close to Neumann conditions. A typical outflow boundary copies the inside state into the halo, while an inflow boundary prescribes selected quantities.

If the flow is close to zero and points inward, it can be useful to add a limiter that clamps or resets the incoming component. This keeps a nominal outflow face from accidentally injecting material or energy.

These simple conditions only control face-connected halo volumes. They do not alter diagonal halo volumes, so strongly oblique information flow is better handled by increasing the domain size or by using a geometry/boundary treatment suited to the application.

More complex boundaries

Boundary conditions that extrapolate data into the outside region need more information than the callback receives directly. In particular, derivative-based conditions need approximations of gradients at the boundary:

\[ Q(x)\vert_{\partial\Omega} = \lim_{x\mapsto\partial\Omega} B(Q(x,t), \nabla Q(x,t)). \]

The common implementation pattern is:

  • Introduce auxiliary variables that store directional derivatives.
  • Compute these derivatives after each time step with a finite-difference reconstruction.
  • Read the stored derivative information in boundaryConditions and use it to set Qoutside.

This approach keeps the boundary callback local while still making the required gradient information available through the solver state.
