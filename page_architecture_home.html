A Peano 4 application is a generated C++ program organised into layers. The Python API describes data, algorithmic steps, and action sets, then emits the stand-alone C++ sources and build files.

Code organisation

The dependency order is tarch, peano4, and then either exahype2 or runner. The application target combines the runner with its selected simulation extension.

  • **Technical architecture (tarch)** provides tasking, MPI wrappers, accelerator support, logging, plotting, and small linear-algebra utilities. It hides backend-specific APIs from the upper layers.
  • **Peano core (peano4)** owns the index-linked spacetree, traversal, rank-boundary exchange, and the pool interface used by generated data. Its sub-package peano4::particles adds the solver-independent particle model, its vertex-associated storage and its sorting.
  • **Extensions (exahype2)** assemble the core facilities into numerical solver families and own the patch operations on top of the spacetree.
  • **Runner (runner)** executes generated program steps, coordinates the SPMD control flow, and reports global statistics.
  • Application code supplies the problem-specific kernels, parameters, and generated project description.

Runtime architecture

Program steps

The generated main registers each algorithmic step as a runner::Step and calls runner::launch(). The global master selects the phase and program step. runner::Engine distributes the same step identifier to every rank, executes the registered body, and synchronises the global statistics afterwards.

A step constructs its observer, calls the static prepareTraversal() hook, passes the observer to peano4::topology::TopologyManager::traverse(), and calls unprepareTraversal() after every observer clone has finished.

Grid representation and data pools

Every MPI rank owns one peano4::topology::TopologyManager. Its peano4::topology::Tree holds flat cell, face, and vertex arrays linked by integer indices. Adjacent cells reference the same face and vertex indices. Periodic boundary entities are aliases of the same indices.

The rank ownership table is identical on every rank, but the materialised structure is not: a rank builds the levels above the spawn level in full and, below it, only its own blocks plus one ring of neighbours. Everything outside that region is answered from the refinement plan by lattice arithmetic instead of being stored. Each cell carries its owning rank, and a traversal skips subtrees that do not touch the local rank. Solver data is allocated only for locally relevant entities in flat pools. peano4::grid::GridTraversalEvent maps tree entity indices to the corresponding rank-local pool slots.

Traversal task graph

peano4::topology::TreeTraversal walks the tree in Peano curve order and emits the established observer callbacks. With several threads, the traversal decomposes the local curve segment into subtree tasks. Spawn-level blocks form the initial task roots, and heavy refined subtrees contribute deeper roots. Each task owns an observer clone and private traversal state.

Standing traversals record their event streams. Later sweeps replay these flat recordings while the task graph schedules independent subtree tasks. A registered data container can reject subtree-task replication; the rank then traverses serially for that step.

Data consistency

Cells have one owning rank. A face or a vertex that two ranks or two subtree tasks hold at the same time keeps a live copy for the current sweep and frozen copies for the partner state. The generated merge callbacks receive partner data before the first local touch that consumes it.

Rank-boundary data is packed once per neighbour rank and data container after a sweep. Non-blocking transfers overlap the following sweep's interior tasks, and boundary tasks wait until the received frozen slots are ready. Intra-rank task interfaces use the same one-sweep-lag merge semantics without MPI.

Regridding

Grid control events update a discrete refinement plan. Before solver data becomes persistent, a changed plan directly rebuilds the tree and runs a creational sweep. With live solver data, a stable single-owner delta appends or prunes in place. Other changes prepare the required migration structures and pool-slot mappings. Both paths emit one transition sweep with the required create and destroy events. The target plan also determines a new weight-balanced rank ownership table.

Python API

The Python API models the generated program at two levels:

  • A domain-specific project describes solvers and application features.
  • A Peano project records data models, algorithmic steps, observers, and action sets.

generate_and_build() emits the C++ observers, repositories, program-step registry, main routine, and build files. Generated observers translate the generic traversal events into the action-set callbacks supplied by the application and its extension.

Build variants

Peano libraries are available in release, asserts, and debug modes. Dimension-dependent libraries carry a 2D or 3D suffix; tarch is dimension-independent.

  • Release removes assertions and debug logging.
  • Asserts enables assertions.
  • Debug enables assertions and debug logging.

Repository organisation

  • src contains the C++ libraries.
  • api contains the Python generators and templates.
  • documentation contains the Doxygen pages and assets.
  • tests contains application and integration test cases.
  • applications contains complete applications.
