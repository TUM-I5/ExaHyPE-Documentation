Some frequently asked questions and problems are discussed below.

CMake

  • How can I tell the code generator which build folder to use?

The build system is CMake only. By default, the Python code generator searches upwards from the current working directory for a PeanoConfig.cmake file and uses the build folder containing it. If there are multiple CMake build folders present (e.g. a GPU build and a non-GPU build), set the environment variable PEANO_BUILD_DIR (or its alias PEANO_CMAKE_BUILD_DIR) to the build folder you want the code generator to use; PEANO_BUILD_DIR takes precedence if both are set. Unsetting the environment variable reverts to the automatic search.

Compilation

  • The translation fails with the error
    '#pragma float_control(precise, off)' is illegal when except is enabled
    We have seen this error with some LLVM-based compilers. Please re-translate with -fno-exceptions. Unfortunately, this disables some error checking in the checkpoint and file output routines. If that does not help, you might want to reduce the optimisation level. On Intel, switching from -fast to -O3 does work in some cases.

  • My C++ version is too old Peano requires C++20, which CMake enforces automatically. If your compiler defaults to an older standard, you can force the flag through

    cmake .. -DPEANO_EXTRA_CXX_FLAGS="-std=c++20"

    Depending on your compiler, the flag might also be

    cmake .. -DPEANO_EXTRA_CXX_FLAGS="--std=c++20"

    Some compilers want you to use two hyphens, others expect one. Most Clang-based compiler installations do not bring their own C++ standard library to the table. They use the pre-existing GCC STL. Now, if your Clang-based compiler - that includes NVIDIA and Intel - is built against a version of GNU whose STL is too old, you will get errors despite the std flag. In this case, you have to load a newer GCC module after you have loaded your Intel, NVIDIA or Clang module. You load the Clang-based compiler which will introduce a GNU STL, i.e. set the corresponding environment variables. After that, you manually load a newer GCC which redirects all of these variables.

    If there are multiple gcc versions present, it is possible for CLANG to automatically select an outdated version thus creates problem when compiling. You can check what is the selection version with clang++ -v. Use this to select the other listed options: --gcc-install-dir=/path/to/new/gcc.

  • My compiler reports
    error: `align_val_t` is not a member of `std`
    We have seen this error with GCC if the supported C++ generation is too old. See remarks above.
  • My compiler yields errors like
    `warning #3191: scoped enumeration types are a C++11 feature`
    Your compiler seems not to have C++11 (or, newer) enabled by default. See remarks above.
  • My compiler fails with
    error: name followed by "::" must be a class or namespace name
    if (not std::filesystem::exists(indexFileName + ".pvd"))
    We have seen this error with GCC if the supported C++ generation is too old. See remarks above.
  • My compiler terminates with
    `error: unknown attribute 'optimize' ignored*`
    We have seen this issue on macOS with CLANG replacing GCC. Unfortunately, CLANG seems to pretend to be GNU on some systems and then the wrong header is included. Consult the remarks on compiler-specific settings. Select the Clang toolchain explicitly via
    .. -DCMAKE_CXX_COMPILER=clang++ -DCMAKE_C_COMPILER=clang
    so that Peano's compiler-specific settings header picks up the correct compiler.
  • My compiler terminates with errors when I enable OpenMP multithreading Use a compiler with OpenMP 5.0 support, such as GCC 9.x.
  • I configured Peano with HDF5, but my application (experiment or benchmark) will not compile HDF5 support is enabled through the CMake option PEANO_WITH_HDF5 (on by default). Peano links only the HDF5 C component (find_package(HDF5 COMPONENTS C)); there is no dependency on the HDF5 C++ binding. The resulting include and link flags are attached to the PeanoOptions interface target and written into PeanoConfig.cmake, which the Python API reads to generate the makefile for your application. If HDF5 is not picked up, reconfigure your build with
    cmake .. -DPEANO_WITH_HDF5=ON
    and re-run your Python scripts so they regenerate the makefile from the updated configuration. If HDF5 lives in a non-standard location, point CMake at it via the standard -DHDF5_ROOT=/path/to/hdf5 hint.
  • The configuration fails for the NVIDIA compiler For NVIDIA, we have to make both the C and the C++ compiler point to the C++ compiler nvc++, as both are passed the same arguments which are actually only understood by the C++ version. So please point both compiler switches to nvc++.
    export NVCPP=/opt/nvidia/hpc_sdk/Linux_x86_64/2022/compilers/bin/nvc++
    cmake .. -DCMAKE_CXX_COMPILER=$NVCPP -DCMAKE_C_COMPILER=$NVCPP ...
    Furthermore, some compute kernels are not available with the NVIDIA tools, as the compiler is pretty picky when it decides which temporary variables it might place on the call stack. This should not affect Peano 4's core, but it can affect some extensions such as ExaHyPE.

  • ***My compiler stops with ***

    /apps/developers/compilers/gcc/13.2/1/default/lib/gcc/x86_64-pc-linux-gnu/13.2.0/../../../../include/c++/13.2.0/chrono:2320:48: error: call to consteval function 'std::chrono::hh_mm_ss::_S_fractional_width' is not a constant expression
    static constexpr unsigned fractional_width = {_S_fractional_width()};

    We have seen this with too new C++ standard libs such as the version 13.2. Use an older one such as 11.2.

  • With Intel's OpenMP, the link fails with an undefined reference to __kmpc_omp_taskwait_deps_51 in the tasking layer

    We have seen this with Intel compiler when you use the Clang LLVM OpenMP runtime, i.e. use -fopenmp. Switch to -fiopenmp instead.

Linking

  • The linking fails for the tutorials even though I've followed all instructions Almost always, this is due to missing packages. You have to configure your build with all packages a given tutorial relies on. Return to your build directory and re-run CMake (or edit the options interactively via ccmake ..) toggling on all PEANO_WITH_* options required, then rebuild with make -j.
  • My linker complains about a missing tbb, even though I do not use Intel's TBB Intel has donated TBB to the open source community and Clang, for example, uses it internally to realise its OpenMP scheduler. Unfortunately, the integration is sometimes not mature, i.e. the compiler then does not automatically add the library to its settings. Reconfigure with
    cmake .. -DPEANO_EXTRA_LINK_FLAGS="-ltbb"
    and you should be fine.
  • If I use Fortran as well, I get errors alike
    undefined reference to for_stop_core
    undefined reference to for_write_seq_list
    This tells you that the linker failed to find the Fortran standard libraries. For the GNU compilers, you need for example the flag -lgfortran while Intel requires -lifcore. Pass them to your build via -DPEANO_EXTRA_LINK_FLAGS="-lgfortran" (or -lifcore). You can add these flags manually via your Python script to the code, but this is a flaw. They belong into the build configuration, not into your Python script.
  • The linker complains about some routines/classes from the technical architectures, but they are definitely there GCC/C++ is extremely sensitive when it comes to the order of the libraries used. You might have to edit your makefile manually to get a "valid" ordering that works. We recommend that you always link from the most abstract library to the lowest level lib. In one ExaHyPE project, e.g., the following order worked whereas all others resulted in linker errors: -lExaHyPEAsserts2D, -lPeanoAsserts2D, -lTarchAsserts. So the link order is high-level extensions, core, tarch. The library name encodes the build mode (Release, Debug, Asserts) and the dimension. The Makefile which is generated by the Python API should follow this convention.

Runtime

  • My unit tests fail in the StackTopologyTest. We have found that GCC's STL is buggy (confirmed in version 9.3.0), although we do not know if this bug is found within the unordered_set, the bitset or the pair implementation. Anyway, a newer version of GCC (12 for example) seem to fix this issue. If you use Intel's toolchain or literally any LLVM, you might have to manually load a newer GNU version after you've loaded your core compiler.
  • sycl-ls shows OpenCL devices and no Level Zero device (Intel PVC) This can happen if the following environment variable was set ZET_ENABLE_PROGRAM_DEBUGGING=1. Unset it to fix the issue.

Python API

  • ***import peano4 yields not found error***. You haven't set your PYTHONPATH properly. It has to point to Peano's api subdirectory. So use something similar to 
         export PYTHONPATH=~/git/Peano/api
  • My installation or paraview complains about ModuleNotFoundError: No module named 'numpy'. For some parts of Peano and its extensions, you need the package numpy. If you don't have numpy on your system install it with either of the following commands: 
         pip3 install --user numpy
    Similar arguments hold for jinja2. Peano's API and all extensions can work without numpy in principle. However, not all features (solvers in ExaHyPE, e.g.) might be available if you have no numpy.
  • The formatting scripts yields error messages. Remove the .formatting_python_env directory and re-run the format.py script. Sometimes, errors can occur if the system python libraries get updated or the user has altered their pythonpath (so the PYTHONPATH variable is best left unmodified.) Removing the .formatting_python_env dir will prompt format.py to re-install all it needs.

Performance analysis

  • The Intel/NVIDIA tools do not provide meaningful insight Read through the vendor-specific supercomputer/tool remarks and pick the vendor-specific built toolchain. After that, profile the code in the profile version. The release builds of the libraries do not yield much additional information for spotting runtime flaws.
  • The Intel/NVIDIA tools yield too much data First, pick the vendor-specific toolchain fitting to your system/compiler. After that, amend your log filter. See Logging, profiling and assertions for more info.

Debugging

  • I can't see my log/trace statements. There's a whole set of things that can go wrong.
    • Translate your main code with a reasonable debug flag. The makefile has to translate your code with -DPEANO_DEBUG=1.
    • Link to libraries which are built with a reasonable diagnostic switch.

MPI troubleshooting

  • My code crashes unexpectedly with malloc/free errors. Please rerun your code with Intel MPI and the flag -check_mpi. You should not get any error reports. If you do, we have had serious problems as some of Peano's classes use MPI_C_BOOL or MPI_CXX_BOOL. They seem not be supported properly.
  • With more and more ranks, I suddenly run into timeouts. Peano has a built-in deadlock detector with a default threshold of 600 seconds inside one wait. Use --deadlockTimeout to raise the threshold or disable it.

C++ core

  • Where is the information whether a point or face is at the boundary or not? Peano does not provide any such feature. Many codes for example use the grid to represent complicated domains, and thus would need such a feature anyway. So what you have to do is to add a bool to each vertex/face and set this boolean yourself.

Parallelisation

  • Why does adaptive refinement need several sweeps? A refinement request names a cell that already exists and can expose one additional level. The next criterion evaluation can then request cells on that new level. A regrid also uses a transition sweep to create and destroy entities while it migrates persistent data into the target rank ownership.
  • Why can the rank partition remain imbalanced? Peano assigns complete spawn-level blocks, or the children of a heavy block, using leaf-cell weights. An indivisible heavy unit limits the attainable balance, and equal leaf weights do not represent solver-specific work such as limiters or particle interactions.
  • Where is the load-balancer configuration? Rank partitioning is part of the spacetree engine. Every rank derives the same ownership table from the rank count and refinement plan; an application does not select a separate load-balancer object.
  • I get a timeout but Peano claims that there are still messages in the MPI queue. How do I know what certain MPI messages tags mean? All tags used in Peano are registered through the operation tarch::mpi::Rank::reserveFreeTag. If you translate with PEANO_DEBUG=1, then you get a list of tag semantics at startup. These lists are the same as the ones you use in release mode, i.e. when this information is not dumped. The info goes straight to cout, i.e. you can't filter it. That's because the tag allocation usually happens before our logging landscape is up and configured properly.

  • I have introduced auxiliary (material) parameters and the code crashes every now and then. Initialise all data in your code. That includes any potential auxiliary variables. We usually use

    for (int i=0; i<NumberOfUnknowns+NumberOfAuxiliaryVariables; i++) Q[i] = 0.0;

    as a first step within initialCondition(). This leaves no garbage in the data. Further to that, also set proper boundary data for any auxiliary value. You might not need these data, as you do not use the auxiliary variables to exchange information between patches, but you have to set proper values nevertheless. Otherwise, all of Peano's assertions will fail as it detects data corruption.

  • My higher order solver yields physically slightly unreasonable data for the Riemann solves. If you use a higher-order scheme Peano has to project your polynomial solution onto the faces. For this, it uses pre-assembled matrices which are stored in double precision. However, round-off errors might lead to situations where you get small deviations—we have seen densities around $-10^{-8}$ for the Euler equations, e.g. Usually, such round-off errors are fine, but you might run into problems if you take the square root of such tiny negative values, e.g. It is therefore important that you apply the maximum function:

Naive code leading into problems: assertion(tarch::la::greaterEquals(p,0.0), p); const double c = std::sqrt( gamma * p * irho );

working code: const double c = std::sqrt(std::max(0.0,gamma * p * irho));
